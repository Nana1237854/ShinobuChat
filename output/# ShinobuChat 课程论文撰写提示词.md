## 项目完整信息（供 Agent 引用）

### 项目定位

ShinobuChat 是一个 AI-Native 智能桌面伴侣应用，以 Live2D 角色为载体，融合大语言模型（DeepSeek）、语音合成（Edge-TTS）、语音识别（FunASR）、口型同步、情绪感知与表情驱动，构建"视觉-语音-对话"三位一体的人机交互体验。

### 技术栈

| 层 | 技术 |
|---|---|
| 后端框架 | FastAPI + Uvicorn (Python 3.11) |
| 数据库 | PostgreSQL + SQLAlchemy |
| 大语言模型 | DeepSeek v4-flash（OpenAI 兼容 API） |
| TTS | Edge-TTS（微软晓晓 zh-CN-XiaoxiaoNeural） |
| ASR | FunASR SenseVoice / Whisper |
| 前端 | React 18 + Vite + TypeScript |
| 渲染引擎 | PixiJS 6 + Live2D Cubism 4 SDK |
| 认证 | JWT + Device Code OAuth2 流程 |
| 部署 | Uvicorn (后端) + Vite Dev Server (前端) |

### 核心功能清单

| 功能 | 描述 |
|---|---|
| 多模态对话 | 文本 + 语音输入，文本 + 语音 + Live2D 表情输出 |
| 路由模式 | Chat（闲聊）/ Agent（工具调用）/ Auto（自动决策） |
| 情绪系统 | AI 生成 [emotion] 标签，驱动 Live2D 8 种面部表情 |
| 流式输出 | SSE（Server-Sent Events）实现文字/TTS 音频分流串行输出 |
| 口型同步 | Web Audio API AnalyserNode 实时 RMS 分析 → Cubism ParamA 驱动 |
| 工具调用 | Function Calling：网页抓取、技能激活、Shell 命令、对话摘要 |
| 技能系统 | 基于 SKILL.md 文件的动态技能加载（天气/晚复盘/待办/灵感/OCR/网页搜索） |
| TTS 分流 | 后端分句 → Edge-TTS 合成 → base64 嵌入 SSE → 前端 Web Audio 顺序播放 |
| Live2D 交互 | 点击交互（糖果/拳头/锤子）、截图、音乐播放、背景切换 |
| 认证与多设备 | Device Code OAuth2 流程，JWT 鉴权 |

### 第二章 智能应用系统的范式转变

```
撰写论文第二章"智能应用系统的范式转变"。本章回答"智能系统与传统系统有什么根本不同"。

要求：从以下 8 个维度对比，每个维度都要有 ShinobuChat 的具体实例，不能只罗列概念。

维度 1：交互方式
- 传统：用户通过菜单/按钮/表单选择操作（"点击式交互"）
- AI-Native：用户用自然语言表达意图，系统推理后响应（"对话式交互"）
- ShinobuChat 实例：用户可以说"帮我查一下纽约天气"而不是点击菜单→选择城市→点击查询

维度 2：系统行为
- 传统：确定性响应（相同输入→相同输出，由 if-else/规则引擎驱动）
- AI-Native：概率性推理（相同输入→可能不同输出，由 LLM 上下文+温度参数决定）
- ShinobuChat 实例：同样问"今天怎么样"，AI 可能回复天气预报、心情问候或闲聊，取决于上下文

维度 3：业务逻辑
- 传统：硬编码的规则和流程（代码 = 业务逻辑）
- AI-Native：通过 Prompt 和上下文工程表达意图和约束（Prompt = 软逻辑）
- ShinobuChat 实例：情绪标签 [happy] 通过 system prompt 约束 AI 行为，而非硬编码 if-else

维度 4：系统集成
- 传统：用户主动触发功能（用户→系统）
- AI-Native：系统主动感知需求并预判（系统⇄用户双向）
- ShinobuChat 实例：检测到 sad 情绪时自动切换柔和语气和 Live2D 悲伤表情

维度 5：测试策略
- 传统：断言式测试（输入→预期输出，pass/fail）
- AI-Native：评估式测试（输出质量的模糊匹配、人工评审、置信度评估）
- ShinobuChat 实例：情绪识别不是 pass/fail，而是匹配度评分

维度 6：演进方式
- 传统：版本迭代，代码修改→发布→部署
- AI-Native：Prompt 优化、知识库更新、模型切换，系统行为可"零代码"调整
- ShinobuChat 实例：切换 DeepSeek 模型只需改配置项 SC_AI_MODEL，无需改业务代码

维度 7：开发模式
- 传统：基于需求规格的瀑布/敏捷开发
- AI-Native：基于"提示工程→效果验证→提示优化"的快速实验循环
- ShinobuChat 实例：情绪系统从关键词匹配迭代到 AI 标签生成，每次迭代只改 prompt 和解析逻辑

维度 8：安全模型
- 传统：基于角色的访问控制（RBAC）、输入校验、SQL 注入防护
- AI-Native：Prompt 约束 + 工具白名单 + 输出审查（"软安全"而非"硬规则"）
- ShinobuChat 实例：shell_command 工具只允许 curl，拒绝管道/重定向等控制操作符；skill 白名单限制可加载的 SKILL.md 范围

```

### 第三章 智能应用核心设计方法论

```

3.1 AI-Native 设计思想（约 800 字）
- AI-Native vs AI-Added 的核心区别：AI-Native 是"以 LLM 为操作系统，功能为应用"；AI-Added 是"传统系统+AI 接口"
- ShinobuChat 的 AI-Native 体现：
  a) 路由系统不是硬编码菜单，而是 RouteMode（auto/chat/agent）由 LLM 判断意图后自动选择
  b) 情绪不是规则引擎而是 LLM 自然输出 [emotion] 标签
  c) TTS 文本处理不是正则替换而是 AI 理解语义后输出适合朗读的文本
- 对比分析：如果 ShinobuChat 用 AI-Added 方式做，会是什么样？（每个功能写死规则）

3.2 渐进式增强路径（约 600 字）
- 增强路线图（用表格呈现）：

| 阶段 | 能力 | 实现方式 | 增强触发 |
|---|---|---|---|
| L1 基础对话 | 文本聊天 | LLM API + SSE 流式 | 项目启动 |
| L2 语音交互 | TTS + ASR | Edge-TTS + FunASR | 用户需要语音 |
| L3 视觉表达 | Live2D 表情 + 口型 | Cubism SDK + Web Audio | 需要情感反馈 |
| L4 工具调用 | Agent + Function Calling | ToolRegistry + Skills | 需要查天气/网页 |
| L5 长期记忆 | 向量检索 + RAG | pgvector + Embedding | 需要上下文延续 |
| L6 多 Agent | 路由 + 专业 Agent | AgentCoordinator | 需要任务分工 |

- 每阶段回答"为什么在这个时点引入"和"没有它系统缺什么"

3.3 意图识别与安全架构（约 600 字）
- 三层意图识别架构：
  L1: Skill 关键词匹配（快速路由，如"天气"→ weather skill）
  L2: RouteMode 分类（chat/agent/auto，由 AI 内部判断）
  L3: LLM 推理（复杂意图由 AI 完整理解）
- 安全架构（双层约束模型）：
  内层（Agent Prompt 约束）：system prompt 限定 Agent 的行为边界——只能执行明确允许的操作、不能访问敏感信息、工具结果需解释而非原样输出
  外层（Skill 白名单 + 工具沙箱）：Skill 只能从 skills/ 目录加载（文件路径约束）、shell_command 仅允许 curl 且拒绝控制操作符（| ; & > < ` $）、fetch_web_page 只允许 http/https 协议
- 对比："只用大模型"（安全不可控）vs"只用硬规则"（失去灵活性）vs ShinobuChat 的"双层约束"

3.4 记忆即个性化（约 500 字）
- 三层记忆模型：
  L1 会话上下文（最近 12 条消息注入 system prompt，即时生效）——已实现
  L2 会话摘要（conversation.summary 字段，跨会话保留）——已实现
  L3 向量记忆（pgvector + Embedding，长期跨会话检索）——待实现
- 记忆触发条件：
  - "上次我们聊到..." → L1 上下文
  - "你今天有什么不同" → L2 摘要
  - "我之前说过的..." → L3 向量检索
- 对比：无记忆系统（每次对话从零开始）vs ShinobuChat 渐进式记忆

3.5 多 Agent 协作（约 500 字）
- 单 Agent 的局限：一个 Agent 既要闲聊又要执行任务，prompt 膨胀、行为冲突
- ShinobuChat 多 Agent 设计：
  Router Agent（意图分类）→ 分发到 Chat Agent（闲聊）/ Task Agent（工具调用）/ Memory Agent（记忆管理）
- Agent 间通信协议：统一 JSON 消息格式，明确的输入/输出接口
- 对比：单 Agent（"什么都做但什么都不精"）vs 多 Agent（"各司其职，协同工作"）
```
